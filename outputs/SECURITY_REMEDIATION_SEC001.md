## Original finding and architecture

SEC-001: **Long-lived credentials readable from WebView storage**. The verified baseline persisted the OpenAI credential under `openai_key` and the RTSP address, potentially containing username/password, under `dashcam_rtsp_url`. Settings prefilled those values. JavaScript attached the retained OpenAI credential to HTTP requests and supplied both retained secrets to the privileged native Drive bridge. The vulnerable implementation was also present in the audited shipped APK. No production credential was used in verification or remediation.

| Flow | Before | After in patched source |
|---|---|---|
| Android retention | Plaintext WebView localStorage | Native private preferences containing authenticated ciphertext only |
| Encryption key | No application encryption | Non-exportable AES-256 key generated by Android Keystore |
| Settings | Prefilled retained plaintext | Configured booleans and empty fields; blank means keep existing; entered fields cleared after save, navigation, and deletion |
| Manual OpenAI / saved-frame requests | JavaScript retrieved the retained key and built Authorization | JavaScript supplies request content; native gateway reads the key and adds Authorization |
| Native Drive | JavaScript supplied retained OpenAI and RTSP secrets | Drive plugin reads both directly from the shared native secret store |
| Browser/PWA | Persistent plaintext credential | OpenAI credential held only in a closure in page memory; no RTSP retention |
| Reset/delete | Web storage cleanup | Native key deletion plus ciphertext cleanup; browser memory and managed web stores cleared |

## Implemented remediation

`NativeSecretStore` uses `AES/GCM/NoPadding`, a fresh randomized IV, a versioned envelope, and additional authenticated data bound to each secret's name. Only hexadecimal ciphertext envelopes are written to `retained_secret_ciphertexts_v1` private preferences. The Keystore alias is an identifier, not key material. Encryption keys are not written to preferences, browser storage, code, assets, or constants. A shared store instance serializes key lifecycle, reads, writes, and reset across native callers.

The new `SecureCredentials` plugin exposes only configured status, legacy migration, replacement, deletion, and the application's OpenAI request operation. There is no plaintext-secret getter. Credential entry and one-time legacy migration necessarily pass newly supplied plaintext from the WebView to native code; native code never returns retained plaintext. Validation bounds credential lengths, rejects malformed RTSP endpoints and invalid OpenAI input, and uses generic errors without embedding inputs.

The OpenAI gateway uses a fixed HTTPS Responses endpoint, the two existing application models, bounded requests/responses, `store=false`, consistent stream flags, disabled redirects, and timeouts. It validates the top-level local application URL; request use also requires a resumed Activity. Native HTTP authentication/error response bodies are suppressed because they may echo credential information. Successful response content and status may return to JavaScript. Native responses are buffered and consumed by the existing nonstreaming/SSE fallback; browser streaming continues through fetch. Native prewarming no longer sends a key through JavaScript.

Native Drive consumes secrets directly and retains the existing explicit same-app service handoff and native inference/RTSP use. Drive status does not return credentials. Existing native RTSP validation/error sanitization, backup exclusions, release bridge logging configuration, and foreground/capture controls were preserved. No backend was introduced.

## Migration and lifecycle

1. On initialization, the broker reads legacy values once and synchronously removes both plaintext localStorage entries before asynchronous native migration.
2. Android migrates valid values into authenticated native ciphertext. A readable existing native credential wins over a stale legacy value.
3. If migration is invalid or fails, plaintext is not restored. If native status remains available, Settings can save replacement credentials. If the native plugin/store itself is unavailable, credential use fails closed. A crash between removal and secure persistence may require reentry.
4. Browser legacy OpenAI values move only to page memory; legacy RTSP values are discarded. The existing browser fragment import is memory-only and removes the fragment immediately.
5. Android restart reads ciphertext natively and exposes only status. Malformed, tampered, swapped, or undecryptable ciphertext is rejected and its entry is removed. A missing Keystore key makes old ciphertext unreadable; it does not trigger any plaintext fallback.
6. Explicit native clear deletes the Keystore key before clearing ciphertext preferences. Subsequent storage generates a new key. Delete-all uses this same native clear operation as part of the existing native-data cleanup. Browser deletion clears the in-memory key and managed stores.
7. The application has no account/logout flow. Secret clear/reset and delete-data are the relevant lifecycle operations; no account feature was added.

Browser credentials are not written to localStorage, sessionStorage, IndexedDB, or app-managed caches. Browser reload/page termination loses the configured credential. Settings explicitly disclose this behavior. Language changes now apply in place so saving language does not immediately destroy the required memory-only browser key. There is no persistent fallback.

## Remaining risks and completion limits

- The shipped audited APK still contains its original vulnerable code. A successfully built, inspected, device-tested replacement is required before deployment closure.
- Android Keystore generation/non-exportability, real native bridge execution, runtime logcat, actual migration across an installed upgrade, and Drive/manual HTTP integration have not been exercised on Android in this session. JVM providers are not Android Keystore evidence.
- Logical localStorage removal cannot guarantee physical erasure of historical WebView database remnants. Existing backup exclusions remain in place. Credentials previously exposed should be treated according to their prior exposure; no real credential was available for this work.
- Entry/migration creates short-lived JavaScript plaintext because the existing UI collects credentials. Those values are not retained or returned by native storage. Native networking/RTSP necessarily uses plaintext transiently in process memory; JVM/JavaScript strings do not guarantee physical zeroization, and already running native work can retain an in-use credential until it stops/completes.
- Top-level local-document checks do not distinguish malicious scripts executing inside that trusted document. Such code may invoke the narrow native operations without receiving stored plaintext. This remediation does not close other script/bridge security findings.
- Browser page memory is accessible to code running in the same page while credentials are in use. The browser cannot provide native-style secure retention, so persistence is explicitly disabled.
- Native manual responses are bounded/buffered; actual device behavior and end-to-end functionality still require the blocked runtime verification.
